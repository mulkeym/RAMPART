RAMPART

Request And Model Prompt Analysis & Routing Tool

A Prompt & Tool-Calling Firewall for LLM API Requests

Browser Extension
1

Page Interception

User visits a supported AI chat site. Extension injects bridge.js into the page, which loads content.js. Content script hooks into fetch() and XMLHttpRequest, monitors clipboard paste and drag-drop events for images.

chatgpt.com claude.ai gemini.google.com chat.asksage.com
2

Prompt Capture

User types a prompt and clicks "Send". The hooked fetch/XHR is intercepted before it leaves the browser. Extension extracts the prompt text using site-specific parsing rules and captures any pasted/dropped images as base64 data URLs.

ChatGPT: messages[0].content.parts Ask Sage: JSON[].message Gemini: FormData f.req Claude: body.prompt
3

Build Evaluation Request

Extension constructs an OpenAI-compatible evaluation request with the extracted prompt text, detected model name, and any captured image content.

POST /v1/rampart/evaluate — Authorization: Bearer <api_key>
RAMPART Server
4

Client Resolution

Match the Bearer token against the PBKDF2-hashed key store. Verify the client is enabled, update last_used_at timestamp and increment total_evaluations counter.

5

Policy Resolution

Determine which policies apply to this client. If the client belongs to a group, use the group's dynamically assigned policies. Otherwise fall back to directly assigned policies, or all enabled policies if none are assigned.

6

Deterministic Checks

Run fast, synchronous checks against all applicable policies. These execute in microseconds and catch obvious violations immediately.

regex pattern matching tool allowlist/denylist model allowlist max message size (chars)

Blocking violation found?

If any deterministic check triggers a block action → fail fast and skip expensive LLM/vision evaluation

No blocking violations — continue to async evaluation

LLM Evaluation

For each policy with type: llm checks, send the prompt to the LLM evaluator.

Standard mode: Full JSON → LLM → {violates, message}

Granite Guardian: Text → logprobs → Yes/No threshold

parallel

Vision Evaluation

For each image in the request (unless skip_vision is set), send the base64 image to the vision evaluator LLM with policy instructions.

Returns: {violates, message} per image

7

Aggregate & Deduplicate

Merge all violations from deterministic, LLM, and vision evaluators. Deduplicate by (policy_id, path, message) tuple. Each violation carries: policy_id, severity, category, message, source, and content path.

8

Decision

If any violation has action: block → decision is "fail". If only warnings or no violations → decision is "accept". Warnings are returned separately.

9

Log & Track

Append evaluation event to evaluations.jsonl with timestamp, client ID, decision, violations, and applied policies. Update client counters: total_evaluations, total_violations.

HTTP Response — JSON {decision, violations, warnings}
Extension Response Handling

Extension Decision Point

The extension reads the decision field from the RAMPART response

🛑

BLOCK

Suppress the original fetch/XHR request. Display a violation overlay modal showing policy name, severity, and description. User must click "Acknowledged" to dismiss.

Prompt is NEVER sent to the AI service.

✅

ALLOW

Release the original fetch/XHR request. The prompt proceeds to the AI chat site as normal. The user's interaction is uninterrupted.

AI responds normally.

User Action
1

Open Extension Popup

User clicks the RAMPART extension icon in their browser toolbar. The popup UI presents enrollment fields.

2

Enter Enrollment Details

User provides: RAMPART server URL, group enrollment key (from their admin), and optionally their email address. A unique device ID is auto-generated.

RAMPART URL Group Enrollment Key Email (optional) Device ID (auto)
POST /v1/enroll — {enrollment_key, user_email, device_id}
RAMPART Server
3

Rate Limit Check

Verify the enrollment request doesn't exceed rate limits. Prevents brute-force key guessing.

4

Match Enrollment Key to Group

Look up the provided enrollment key across all groups. The key must match an enabled group's enrollment_key field.

5

Create Client Record

Generate a new API key, hash it with PBKDF2, and create a client record assigned to the matched group. If re-enrolling (same device_id), the existing client is updated with a new key.

API key generated PBKDF2 hash stored Group policies inherited Saved to clients.json
6

Return Plaintext API Key

The newly generated API key is returned once in plaintext. This is the only time it's visible — the server only stores the hash.

HTTP Response — {api_key, client_id, group_name}
Extension Stores Credentials
7

Persist in Browser Storage

Extension saves the API key and RAMPART URL to chrome.storage.sync (or Firefox equivalent). These persist across browser sessions and sync across devices.

8

Extension Active

Popup shows "Enrolled" status with the group name. The extension is now active on all supported AI chat sites and will evaluate prompts before they're sent.

API key in Authorization header Site configs fetched on page load Live CSS/JS updates from server

Optional: CAC Identity Binding

If the RAMPART server has mTLS enabled on port 8443, the extension can additionally call /whoami to bind the enrollment to a CAC certificate identity (X.509 subject). This provides cryptographic proof of the user's identity for DoD/Gov environments.

How RAMPART determines which policies to apply for each request — from API key through user identity, group membership, and policy assignment.

Request Arrives
Identity Resolution
Policy Selection
Step 1 — Client Authentication

API Request

Request arrives at /v1/rampart/evaluate or /v1/chat/completions with:

Authorization: Bearer <api_key>
"user": "jsmith@dha.mil"

Resolve Client

Match the Bearer token against PBKDF2 key_hash store in clients.json. Returns the ClientRecord with:

client.idclient.group_idclient.policy_ids
Step 2 — User Group Resolution (if enabled)

Extract User Field

The OpenAI "user" field (email) is extracted from the request payload.

e.g. jsmith@dha.mil

External Group Lookup

If User Group Resolver is enabled, query the identity provider (Keycloak / AD / PingFederate) for the user's group memberships.

Check in-memory cache (TTL)
Cache miss → provider API call

Returns external groups:

DHA-ClinicalDHA-Admin

Map to RAMPART Groups

Look up external group names in the Group Mappings table (group_mappings.json):

DHA-Clinical → clinical-staff
DHA-Admin → admin-unrestricted

Each RAMPART group has assigned policies. The union of all matched groups' policies is used.

Step 3 — Policy Selection (Precedence)

Policy Resolution Precedence

1. User Groups

If the user field is present, the resolver is enabled, and group mappings match — use the union of all mapped RAMPART groups' policies. This replaces the API key baseline.

2. Client Group

If no user resolution (disabled, failed, or no match), check if the client has a group_id. If so, use that RAMPART group's policies.

3. Direct Assignment

If the client has no group, use the client's directly assigned policy_ids list.

4. All Enabled

If the client has no group and no direct policies, fall back to all enabled policies in the system.

Step 4 — Evaluate Against Resolved Policies

Policy Engine

The resolved policy list is passed to the PolicyEngine which runs:

Deterministic checks (regex, tools, model, size)
LLM evaluation (if no deterministic block)
Vision evaluation (parallel with LLM)

Returns: decision (accept/fail) + violations[]

Step 5 — Log & Track

Prompt Log Entry

Every evaluation is logged with full context:

user identityclient_id resolved external groupsmapped RAMPART groups per-policy pass/failfull prompt content decision + violationseval timing

Forwarded to syslog/Splunk in CEF format if enabled.

Example: Ask Sage User Evaluation

1. Ask Sage sends a prompt to RAMPART with API key Bearer ask-sage-key and "user": "jsmith@dha.mil"

2. RAMPART authenticates the API key → resolves to client ask-sage (baseline policies: all enabled)

3. User Group Resolver looks up jsmith@dha.mil in Keycloak → returns groups [DHA-Clinical, DHA-Admin]

4. Group Mappings: DHA-Clinical → clinical-staff, DHA-Admin → admin-unrestricted

5. clinical-staff has policies [no-pii, hipaa-compliance]; admin-unrestricted has [prompt-injection-defense]

6. Union: prompt is evaluated against [no-pii, hipaa-compliance, prompt-injection-defense]

7. If Keycloak was unreachable, RAMPART would fall back to client ask-sage's baseline policies instead
